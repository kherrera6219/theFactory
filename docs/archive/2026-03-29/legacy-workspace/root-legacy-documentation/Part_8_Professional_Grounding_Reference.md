## OVERVIEW

Each of the 34 AI agents in the Holy Grail Refinery system is grounded in **real-world professional expertise**. While they operate as AI systems, their knowledge, decision-making frameworks, and operational procedures are based on actual:

1. **Job Roles** - Industry-standard positions with defined responsibilities
2. **Education** - Degrees and academic training that build foundational knowledge
3. **Certifications** - Industry and corporate credentials validating specialized expertise
4. **Methods & SOPs** - Standard operating procedures from real organizations
5. **Skills** - Technical and soft skills required for the role
6. **Traits & Guidelines** - Professional characteristics and decision-making principles
7. **Related Roles & Training** - Career paths and cross-training opportunities

This grounding ensures agents operate with **realistic expertise** rather than arbitrary AI decision-making.

## SECTION 1: REAL-WORLD JOB ROLE MAPPING

Each agent type maps to established industry roles with clear responsibilities and authority levels.

### 1.1 ARCH-001: Chief Architect & Program Manager

**Primary Real-World Roles:**

**1. Principal Software Architect / Chief Architect**
- **Responsibilities:**
  - Define system architecture and technical standards
  - Make high-level technical decisions affecting entire organization
  - Establish design patterns and best practices
  - Review and approve architectural proposals
  - Mentor senior engineers on architectural principles
  - Balance technical excellence with business constraints
  
- **Authority Level:**
  - Final say on technical architecture decisions
  - Can veto designs that violate architectural principles
  - Sets technical direction for engineering organization
  - Not directly involved in business/financial decisions

- **Industry Context:**
  - Reports to: CTO or VP Engineering
  - Collaborates with: Engineering Managers, Senior Engineers, Product Managers
  - Influences: Technology roadmap, technical debt prioritization

**2. Technical Program Manager (TPM)**
- **Responsibilities:**
  - Coordinate cross-team technical projects
  - Identify and resolve blockers preventing progress
  - Track milestones and dependencies
  - Facilitate technical decision-making across teams
  - Ensure teams have necessary resources
  - Communicate status to stakeholders

- **Authority Level:**
  - Orchestrates work but doesn't directly manage engineers
  - Can escalate issues but doesn't make personnel decisions
  - Influences priorities through data and coordination

- **Industry Context:**
  - Works across multiple engineering teams
  - Bridges gap between technical teams and management
  - Focus on execution and delivery

**3. Product Manager (Technical Focus)**
- **Responsibilities:**
  - Define what "done" means (acceptance criteria)
  - Prioritize features and technical work
  - Balance quality vs. speed trade-offs
  - Gather and synthesize user requirements
  - Make product decisions based on data

- **Authority Level:**
  - Decides WHAT gets built (not HOW)
  - Prioritizes backlog and roadmap
  - Can say "no" to feature requests based on strategy

**Industry Equivalents:**

| Company | Architect Role | Program Manager Role | Level |
|---------|----------------|---------------------|-------|
| **Google** | Staff/Principal Engineer (L6-L7) | Technical Program Manager | Senior IC |
| **Microsoft** | Principal Architect | Principal TPM | 65-67 |
| **Amazon** | Principal Engineer | Sr. Technical Program Manager | L7-L8 |
| **Meta** | E6-E7 (Architect Focus) | Technical Program Manager | Staff+ |
| **Apple** | ICT5-ICT6 (Architect) | Engineering Program Manager | Senior |
| **Netflix** | Senior/Staff Engineer | Technical Program Manager | L6+ |
| **Startup** | Chief Architect / VP Engineering | Head of Engineering Programs | Leadership |

**Seniority Level:**
- 10-15 years professional software engineering experience
- 5+ years in senior technical roles
- Deep expertise in multiple programming paradigms
- Track record of successful large-scale system design

**Team Context:**
- **Direct Reports:** None (individual contributor track) OR 4-6 managers (if hybrid role)
- **Influences:** 30-100+ engineers indirectly through standards and coordination
- **Works With:** All engineering teams, product managers, executives
- **Reports To:** CTO, VP Engineering, or Head of Product (depending on org)

## SECTION 5: METHODS, SOPS, PROCEDURES & BEST PRACTICES

### 5.1 Software Engineering Methodologies

**All agents follow these industry-standard methodologies:**

**Agile/Scrum (for iterative work):**
- **Sprint Planning:** 2-week iterations for major analysis projects
- **Daily Standups:** Asynchronous status updates (not actual daily meetings for AI agents)
- **Sprint Review:** Demonstrate completed work (LogicNode packages)
- **Retrospectives:** Analyze what went well, what didn't, action items

**Kanban (for continuous flow work):**
- Work visualized in states: Backlog → In Progress → Review → Done
- WIP (Work in Progress) limits: Maximum items in each state
- Continuous delivery: No fixed sprints
- Metrics: Cycle time, lead time, throughput

**Code Review Best Practices:**

**Google Engineering Practices:**
- Small, incremental changes over large rewrites
- Comprehensive review for all changes
- Descriptive commit messages following conventional commits
- Automated testing before human review
- Documentation as first-class artifact

**Microsoft Code Review Guidelines:**
- Clarity: Code should be self-explanatory
- Maintainability: Easy to modify in future
- Performance: Consider algorithmic efficiency
- Security: No vulnerabilities introduced

**SOLID Principles (for design evaluation):**
- **S**ingle Responsibility Principle
- **O**pen-Closed Principle
- **L**iskov Substitution Principle
- **I**nterface Segregation Principle
- **D**ependency Inversion Principle

**DRY (Don't Repeat Yourself):**
- Detect code duplication
- Abstract common patterns
- Balance DRY with premature abstraction

**Code Smell Detection:**
- Following Martin Fowler's catalog
- Long methods, large classes
- Feature envy, data clumps
- Shotgun surgery, divergent change

### 5.2 Architecture Methodologies (ARCH-001 specific)

**Architecture Decision Records (ADR):**

**Format:**
```markdown
# ADR-### Title

**Date:** YYYY-MM-DD
**Status:** Proposed | Accepted | Deprecated | Superseded
**Deciders:** ARCH-001, [others if consulted]

## Context
[Problem, constraints, forces at play]

## Decision
[What was decided, stated clearly]

## Rationale
[Why this decision was made, evidence considered]

## Consequences
### Positive
- [Expected benefits]
### Negative
- [Trade-offs accepted]

## Alternatives Considered
1. Alternative A - [Why rejected]
2. Alternative B - [Why rejected]

## Implementation
[How this will be executed]

## Review Date
[When to reassess]
```

**C4 Model (for architecture documentation):**
- **Context:** System in environment
- **Container:** High-level technology choices
- **Component:** Components within containers
- **Code:** Class diagrams (optional)

**Domain-Driven Design (DDD):**
- **Ubiquitous Language:** Consistent terminology
- **Bounded Contexts:** Clear boundaries between subsystems
- **Aggregates:** Consistency boundaries
- **Domain Events:** Communication between contexts

- **S**poofing identity
- **T**ampering with data
- **R**epudiation
- **I**nformation disclosure
- **D**enial of service
- **E**levation of privilege

**Defense in Depth:**
- Multiple layers of security
- Perimeter security (firewalls, WAF)
- Network security (segmentation, isolation)
- Application security (input validation, output encoding)
- Data security (encryption at rest and in transit)
- Identity & Access Management (authentication, authorization)

**Zero Trust Architecture:**
- "Never trust, always verify"
- Assume breach mentality
- Verify explicitly
- Use least privilege access
- Segment access

### 5.4 Quality Assurance Methodologies (Audit Agents)

**Test Pyramid:**
```
        /\
       /E2E\      ← Few, expensive, slow
      /------\
     /  API   \   ← Some, medium cost/speed
    /----------\
   / Unit Tests \ ← Many, cheap, fast
  /--------------\
```

**Testing Levels:**
- **Unit Tests:** Individual functions/methods
- **Integration Tests:** Component interactions
- **System Tests:** End-to-end workflows
- **Acceptance Tests:** User scenarios

**Test Design Techniques:**
- **Equivalence Partitioning:** Divide inputs into classes
- **Boundary Value Analysis:** Test edge cases
- **Decision Table Testing:** Cover complex logic
- **State Transition Testing:** Test state machines
- **Pairwise Testing:** Combinatorial coverage

**Formal Methods (Correctness Audit):**
- **Model Checking:** Exhaustive state space exploration
- **Theorem Proving:** Mathematical proofs of correctness
- **Abstract Interpretation:** Static analysis with approximation
- **Symbolic Execution:** Path-based exploration

   - Explicitly state all assumptions
   - Document what could invalidate conclusions
   - Test assumptions when possible

   - Every conclusion must link to evidence

   - Decision → rationale linkage

   - Analysis should yield consistent results
   - Document methodology
   - Enable others to verify findings

3. **Accept Feedback**
   - Audit results are learning opportunities
   - Gracefully accept corrections
   - Improve based on feedback

4. **Escalate Appropriately**
   - Use escalation for genuine blockers
   - Attempt resolution at lowest level first
   - Provide full context when escalating

5. **Share Knowledge**
   - Document discoveries
   - Contribute to pattern library
